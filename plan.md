# PLAN-U08 — Gold star schema

## Facts this plan rests on

- Fabric Data Warehouse, read 2026-10-28 from Microsoft Learn "Data types" (ms.date 2026-06-11)
  and "T-SQL surface area" (ms.date 2026-09-16):
  - Tables support `varchar`, `char`, `date`, `datetime2` (≤ 6 fractional digits), `smallint`,
    `int`, `bigint`, `decimal`, `bit` and `float`.
  - Not supported: `nvarchar`, `datetime`, `money` or `tinyint`.
  - Primary, unique and foreign keys exist only `NOT ENFORCED`, which SQL Server does not parse.
  - Supported: `TRUNCATE`, `MERGE`, `IDENTITY`, stored procedures, views and session #temp tables.
  - Not supported: synonyms, triggers, recursive queries.
  - Lakehouse strings surface as `varchar` with `Latin1_General_100_BIN2_UTF8` collation.
- The Warehouse reads Lakehouse tables in the same workspace by three-part name
  (`lh_silver.dbo.<table>`). SQL Server cannot read Delta.
- Silver (U06, U07) holds history; the analytical window is 2024-10-01 … 2026-09-30
  (`config/sources.yaml`) and is applied in Gold.
- ADT events: A01 admits to (ward, bed), A02 moves to (ward, bed) from (from_ward, from_bed), A03
  discharges. Stays still open on 2026-09-30 have no A03.

## Approach A — Stored-procedure full reload in T-SQL (taken)

- `sql/gold/` holds the Gold DDL (`gold` schema, no key constraints, because `NOT ENFORCED` does not
  run on SQL Server) and a procedure `gold.reload` that truncates and refills every table from a
  `silver` schema.
  - In Fabric, `silver` holds views over `lh_silver.dbo.*` (`sql/fabric/silver_views.sql`).
  - Locally, `silver` holds tables copied from the Delta Silver by `scripts/gold.py`.
  - The same `gold.reload` runs on both. The local database uses the Fabric collation
    `Latin1_General_100_BIN2_UTF8`.
- Dimensions: `dim_date` (window, generated by cross-joined digits, not recursion), `dim_clinic`,
  `dim_ward`, `dim_bed`, `dim_patient` (one row per master patient, demographics from the
  preferred record: EHR, then billing, ADT, lab), `dim_payer`, `dim_diagnosis`.
- Facts (window only): `fact_encounter`, `fact_bed_day` (per stay segment and calendar day,
  occupied hours), `fact_claim`, `fact_lab_result`, `fact_ed_visit`. Every fact row carries
  `master_patient_id` through `silver.patient_xref`.
- Files: `sql/gold/*.sql`, `sql/fabric/silver_views.sql`, `.sqlfluff`, `scripts/gold.py`,
  `src/clinic_chain/stand.py` (gold database), `tests/test_gold.py`, `docs/adr/0002-lakehouse-
  warehouse.md`, `Makefile` (`gold`), `.github/workflows/ci.yml`, `README.md`, `CLAUDE.md`,
  `plan.md`.
- Invariants: keys unique (tested, not declared); every fact row has a dimension row; the
  T-SQL avoids every construct listed above as unsupported.
- Red check: `stand` test reconciling Silver → Gold: per fact, Gold rows equal Silver rows
  inside the window. Bed-day hours equal the stay segment hours computed independently in Spark,
  and every fact key resolves in its dimension. The fast test runs sqlfluff (tsql dialect) through
  `make lint`.
- Reverse: drop schema `gold`, delete `sql/`.
- Pipeline wiring (a Warehouse stored-procedure activity after `run_nb_mpi`) is left to U19 with the
  other deploy-time items.

## Approaches not taken

- **B. Gold as Delta tables built in PySpark.** This contradicts the intent: the Warehouse carries
  DDM and CLS (U16) and T-SQL is a stated skill.
- **C. dbt-fabric.** It adds a tool the intent does not name, and the deadline does not allow it.

## Implementation notes (2026-10-28)

- The procedure is `gold.reload`: sqlfluff's T-SQL parser rejects `gold.load` (`LOAD` is a keyword).
- Bulk copy into UTF-8 `varchar` corrupts non-ASCII names (`Beltrán`). The local copy of Silver
  therefore uses `nvarchar`; Gold tables stay `varchar`, and a test checks that non-ASCII names
  arrive intact in `dim_patient`.
- `occupied_hours` is `decimal(12, 6)`. At 4 decimals the summed rounding allowance (35k rows)
  exceeded one hour, and a +1 hour corruption passed the test. Now it fails.
- Full population: `make gold` takes 28 s.
  - Facts: `fact_encounter` 10,371, `fact_bed_day` 35,120, `fact_claim` 32,722,
    `fact_lab_result` 59,083, `fact_ed_visit` 11,445 (one arrival before the window).
  - `dim_patient` 15,330.
- Negative controls:
  - deleting one claim fails the reconciliation test;
  - adding one hour to one bed-day row fails the bed-hours test.
